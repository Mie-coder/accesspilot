# AccessPilot MVP 设计语言卡

## 1. 设计意图与目标用户

AccessPilot 是一套虚构企业权限申请演示工作台。申请人要清楚自己正在填写什么、是否已提交；审批人要快速判断风险并作出有序决策；审计查看者要能追溯每次状态变化。界面首先传达可信、可控和可追踪，而不是“AI 很炫”。

## 2. 核心任务流与范围

主流程：创建 Demo Workspace → 对话补全草稿 → 明确确认 → 风险审查 → 经理审批 → 数据所有者审批 → 幂等开通 → 查看审计时间线。

MVP 包含对话申请台、审批收件箱、申请与审计详情三页。暂不包含真实企业登录、真实 IAM、组织通讯录或生产级租户管理。

## 3. 核心设计原则

- 状态先于装饰：草稿、审批和开通状态始终可见，并使用不同语义。
- 一个页面一个主动作：申请台是“继续/确认”，收件箱是“审批”，详情页是“恢复/查看”。
- 证据贴近决策：政策引用、风险理由和审计事件靠近相关操作展示。
- AI 只占对话区：业务事实卡、审批表和审计时间线使用确定性 React 组件。

## 4. 视觉方向

- 气质词：克制、可信、清晰。
- 方向：浅色冷中性企业工作台，单一青绿色强调色；成功、警告、错误使用独立语义色。
- 避免：AI 紫色渐变、玻璃拟态堆叠、悬浮大卡片墙、把所有状态都做成聊天气泡。
- 排版：系统无衬线字体；页面标题、区块标题、正文、元信息、代码/编号五种稳定角色。
- 形状：内容面板 12px 圆角、输入 8px、操作按钮 8px；状态标签使用胶囊形。

## 5. 交互与动效

- 状态变化使用 150–220ms 的淡入与位置微移，表达层级和反馈。
- 提交、审批和重试都有明确的进行中、成功和失败反馈。
- 支持 `prefers-reduced-motion`，关闭非必要位移动画。

## 6. 组件策略

- 对话线程、消息、Composer 和 Tool UI 使用 `@assistant-ui/react`。
- 使用 `LocalRuntime + ChatModelAdapter` 对接自有 FastAPI/SSE。
- 草稿卡、审批表、状态条和审计时间线使用项目自有 React 业务组件。
- 不使用 assistant-ui Cloud 保存申请、审批、授权或审计事实。
- 现有 Vite 项目使用 CSS 变量与模块化原生 CSS，不额外引入第二套大型设计系统。

## 7. 页面、真实状态与适配

- 对话申请台：桌面为导航 / 对话 / 草稿状态栏；移动端按对话、草稿摘要、操作顺序单列。
- 审批收件箱：桌面列表详情分栏；移动端列表进入详情。
- 申请详情：顶部状态摘要，中部审批与政策证据，底部只追加审计时间线。
- 每页覆盖加载、空、错误、只读回放和成功状态。
- 键盘焦点可见，按钮和字段有可访问名称，正文与控件满足 WCAG AA 对比度。

## 8. 应该做与不该做

- 应该持续区分“草稿完整”“已提交”“审批通过”“已开通”。
- 不应该把模型隐藏思维链、密钥、内部异常栈或未确认的业务事实发送到浏览器。
- 不应该为展示效果伪造成功状态或统计数字。

## 9. 视觉验收

- 重点检查 1440×900、1024×768 和 390×844。
- 黄金路径的所有状态必须真实来自 API，不能依赖静态 mock。
- 核心操作可用键盘完成，错误和恢复入口在目标尺寸下可见。

## 10. 基线刷新

- 慢变化层：状态语义、信息层级、可访问性、组件职责。
- 快变化层：assistant-ui API、图标和前端构建工具；实现前核对官方文档和当前包版本。
